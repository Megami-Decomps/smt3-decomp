# smt3-decomp project notes

Matching decompilation of Shin Megami Tensei III: Nocturne (USA), `SLUS_209.11`,
SHA-1 `5facfbf7916836613449c922e26a4ec412207b32`, 4551696 bytes. One version key:
`smt3`.

## Provenance

The build system, tool set and documentation structure are vendored from
[dds-decomp](https://github.com/Megami-Decomps/dds-decomp) (redthing1) and adapted
for one version. DDS1/2 are built on this engine, so its findings about ee-gcc 2.96,
ee-as and the sdf engine usually transfer. When a doc states something that was
measured on DDS and not on this ELF, it says so; keep that distinction when editing.

## The ELF is reproduced as a flat image

Every file-backed section has the same vram minus file offset delta, `0xff000`, so
the build links an ELF and `objcopy -O binary` turns it into a byte-identical copy of
the retail file. That only holds while the splat config covers all of
`[0x0, 0x457410)`: the ELF header, the loaded sections, and the trailer after
`0x452b55` (`.DVP.*` overlay tables, `.shstrtab`, the section headers). A segment
added without keeping that coverage breaks the checksum in a way the per-unit diff
will not show.

`.vutext` and `.vudata` are VU1 microcode and its data. They stay binary blobs and
must never be disassembled as MIPS.

## Names come from the IDB, boundaries do not

`config/smt3/symbol_addrs.txt` is generated by `tools/ida_symbols.py` from the open
IDA database, which carries SMT3HD symbol recovery (9470 of 9571 functions named).
Regenerate it rather than editing the generated block; hand-curated symbols go above
`// BEGIN ida` and win.

Every `mcp__ida__*` call and `ida.py` invocation needs `instance=SLUS_209.11`.
Ports are assigned in open order and move between sessions, so address the IDB by
module name, never by number. Omitting it, or reusing a port from an earlier
session, silently targets a different game's database.

Three other Nocturne builds are often open: `SLPM_652.42` (Dec 2002 JP debug),
`SLPM_654.62` (Maniax) and `SLPM_666.81` (Maniax Chronicle). The last two now carry
the USA names, carried over by `tools/pair_build.py`, so a call that lands on the
wrong one answers with plausible names at the wrong addresses. Name the build you
mean. What those builds are good for: `docs/maniax-build.md`.

The IDB is read-only for ordinary work: never patch, define or save through it. The
one exception is correcting a name or type the retail code proves wrong, which is
expected rather than optional, because `symbol_addrs.txt` is generated from the IDB
and a correction made only in the generated file is lost on the next export. Correct
it in the IDB, re-run `tools/ida_symbols.py`, and verify the build still matches.
Rename only what the code proves: an allocation site, an init function, a stride, a
caller. Confirmed cases so far are recorded in `docs/idb-corrections.md`.

`.text` is split into 204 units, 195 under recovered names and the rest still called
`code_<vram>`. Twelve of them are the Sony SDK and C runtime under `src/smt3/sdk/`,
which `config/smt3/compilers.txt` builds with ee-gcc 2.9 rather than 2.96; see
`docs/sdk-matching.md`. Moving a boundary or naming a unit needs evidence from
`tools/find_tus.py`, the IDB or an HD source run, not a guess, and the relinked image
must stay byte-identical afterwards: see `docs/tu-recovery.md`.

## Remote

`origin` is <https://github.com/Megami-Decomps/smt3-decomp>, public. Push `main` there;
nothing from the retail game is tracked, so check that before adding anything under
`orig/` or a new build directory.
